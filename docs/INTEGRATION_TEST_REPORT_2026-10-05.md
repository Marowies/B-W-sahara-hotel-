## بيئة الاختبار

- PHP 8.3.35 والاعتماديات المحدثة في تثبيت التحليل المنفصل.
- MariaDB **11.8.9** مع InnoDB، وهو الإصدار المذكور في ترويسة ملف SQL المقدم. نسخة محمولة من [أرشيف MariaDB الرسمي](https://archive.mariadb.org/mariadb-11.8.9/winx64-packages/) مع مطابقة SHA256 قبل تشغيلها.
- قاعدة جديدة باسم `hotel_test_integration_20261005`، واتصال loopback على `127.0.0.1:24406`؛ دون خدمة Windows مثبتة أو تعديل إعدادات التطبيق.
- مخطط مصغر للجداول المستخدمة في الاختبارات وبيانات اصطناعية. لم يتم تطبيق كامل migrations أو استعادة dump الإنتاج؛ لذلك هذه ليست شهادة توافق كاملة للمخطط والبيانات الحقيقية.
- منطق الفندق وPayPal وStripe الفعلي من نسخة العمل. اتصالات التقويم وPayPal مستبدلة بردود محلية؛ توقيع Stripe يتم إنشاؤه والتحقق منه بواسطة SDK الحقيقي بمفتاح اصطناعي.
- نموذج hooks يسجل الأحداث الصادرة ولا ينفذ دورة البريد أو جميع hooks الخاصة بالإنتاج. اختبارات الدفع تثبت سلوك الخدمة/الكنترولر وحدود الثقة، ولا تثبت خصمًا ماليًا أو تسوية مع مزود خارجي.

## التزامن: ما نجح وما فشل

**نجح checkout الداخلي وحده:** أربع عمليات PHP منفصلة بدأت معًا لشراء آخر غرفة، مع تأخير قصير بعد قفل صف الغرفة لإجبار بقية العمليات على الانتظار. نجحت عملية واحدة، ورفضت الثلاث الأخرى، وكانت الكمية المحفوظة **1 من سعة 1**.

**فشل checkout مع استيراد التقويم:** بدأ استيراد حدث خارجي بعد قراءة checkout للمخزون، وقبل حفظه. تم تنسيق هذا التداخل بحاجز بين عمليتين مستقلتين، وليس بمجرد تغيير البيانات بالتتابع في عملية واحدة. checkout رجع `booked` والاستيراد رجع `imported`؛ المحفوظ النهائي **2 من سعة 1**. `ICalService::createBlockedDate` لا يشارك قفل الغرفة الذي يستخدمه checkout، ولذلك لا تكفي سلامة checkout وحده لحماية جميع مسارات الكتابة.

هذا اختبار لتداخل محدد على مستوى الخدمة والكنترولر باستخدام InnoDB، وليس اختبار ضغط HTTP أو برهانًا على كل الجداول وكل حالات التزامن في الإدارة.

| IT-07 | P1 عند تفعيل PayPal الداخلي | callback token مختلف عن order المخزن في الجلسة قُبل عندما نجحت استجابة capture المحاكاة | `PayPalPaymentAbstract::getPaymentStatus`: مطابقة token/order/session والتحقق من الهوية قبل المعالجة |
| IT-08 | P1 عند تفعيل PayPal الداخلي | بعد capture محاكى مكتمل بقيمة 200 USD، وصل للحدث `PAYMENT_ACTION_PAYMENT_PROCESSED` المبلغ 0.01 EUR وorder_id=99999 المرسلة في callback | `PayPalPaymentService::afterMakePayment`: بيانات الحجز من الربط المحفوظ بالسيرفر والتحقق من مبلغ/عملة/هوية capture؛ عدم الاعتماد على query parameters |
| IT-09 | P2 | إعادة نفس Stripe event الموقّع أطلقت حدث إتمام الدفع مرتين | `StripeController::webhook`: idempotency دائمة للحدث وانتقال الحالة، مع transaction وقفل مناسب |
| IT-10 | P2 | Stripe webhook موقّع بقيمة مختلفة عن payment المخزن جعل الحالة completed | مقارنة المبلغ المستلم والعملة والهوية بسجل الدفع؛ رفض عدم التطابق وإرساله للمراجعة |

P1 هنا يعني خللًا مؤثرًا في المخزون أو ربط الدفع يستحق الإصلاح أولًا. P2 يحتاج المعالجة قبل الاعتماد على المسار في التشغيل. مشاكل PayPal مثبتة محليًا في الكود الداخلي، وليست دليلًا على استخدامها أو استغلالها في موقع الفندق الذي يحيل إلى Aiosell. اختبار اختلاف مبلغ Stripe يستخدم حدثًا صحيح التوقيع اصطناعيًا؛ لم يتجاوز التوقيع أو يثبت قدرة مهاجم خارجي على توقيع أحداث حقيقية.

ربط الدفع بالفندق حساس لأن `Hotel/Providers/HookServiceProvider` يستقبل `PAYMENT_ACTION_PAYMENT_PROCESSED` ويستدعي حفظ الدفع ثم معالجة الحجز برقم order الصادر في الحدث. هذا الربط تمت مراجعته من المصدر؛ لم تُشغل سلسلة hooks كاملة ببيانات الفندق ضمن هذا الاختبار.

1. استيراد حدث تقويم سليم حفظ `[10 نوفمبر، 12 نوفمبر)` دون ليلة إضافية، وتكرار نفس المصدر والتواريخ لم ينشئ نسخة ثانية، وتم تحديث وقت المزامنة.

تم التحقق من تركيب ملفات الاختبار الأربعة وrunner الأمان، وفحص `git diff --check` دون أخطاء. قاعدة الاختبار أزيلت بعد حفظ النتائج والخادم المؤقت أوقف؛ لم تُترك خدمة تطوير تعمل.

## ما لم يمكن اختباره الآن

**الدفع عبر Sandbox الحقيقي لم يُختبر** لأن المستخدم أكد عدم توفر إعداداته. لم يتم استخدام مفاتيح الإنتاج كبديل. لا يوجد كذلك اختبار Aiosell API أو redirect موثق بالبارامترات، أو معاملات Stripe/PayPal حقيقية، أو إشعارات مزود خارجي، أو refund/تسوية مالية.

اختبارات المتصفح الكاملة والبريد وOAuth واستعادة كامل قاعدة الإنتاج ومسارات الإدارة المتزامنة ليست ضمن الحالات المنفذة. الخطوة التالية في الإصلاح: IT-01 ثم IT-02..06، ثم ربط الدفع الداخلي IT-07..10 إذا سيُستخدم، وبعدها إعادة الحالات نفسها وإضافة Sandbox عند توفره.
