## 1. الحكم الهندسي

المشروع أساسه Laravel 12.43.1 وBotble CMS، بثيم Riorelax وإضافة Hotel. فيه بنية إدارة محتوى وصور وترجمات وصلاحيات قابلة للاستفادة؛ لا توجد قرينة تفرض إعادة بناء كل شيء من الصفر. لكن اعتماد التصميم وحده لا يجعل النسخة جاهزة للإطلاق: اختبارات معزولة أكدت مشاكل تمس الحجوزات وبيانات النزلاء، بالإضافة إلى مشاكل ترجمة وتسعير وتبعيات.

أعلى الأولويات المقترحة بعد مراجعتك للتقرير:

1. حماية تقويم الحجوزات العام ومنع نشر بيانات النزلاء.
2. إعادة حماية CSRF للوحة الإدارة في وضع الإنتاج.
3. منع التحكم في حالة الحجز وعميله من الطلب العام، وربط checkout بمعايير جلسة الحجز وإعادة التحقق من المخزون.
4. مراجعة تنبيهات التبعيات وتحديد ما يصل إليه المستخدم بالفعل، مع تحديثات متوافقة مع Botble واختبارات ارتداد.
5. إصلاح نقل البحث إلى Aiosell، ثم التسعير والترجمة والبريد وتجربة الموبايل.

هذه أولويات هندسية، وليست تغييرات تم تنفيذها أو موافقة نهائية من الفندق. لم أختبر استغلالًا على الموقع الحي أو على Aiosell.

## 4. التشغيل ومنهج الاختبار

- لم يكن PHP أو Composer متاحًا على PATH، وDocker daemon لم يكن يعمل. تم تجهيز PHP 8.3.35 وComposer في أدوات مراجعة منفصلة. تحقق SHA-256 لحزمة PHP طابق القيمة الرسمية.
- تم نسخ ملفات التطبيق إلى sandbox؛ لم تُنسخ `.env` الإنتاجية أو قاعدة الفندق أو سجلاته إلى التطبيق الذي يعمل.
- استخدمت تبعيات PHP الموجودة من النسخة الأصلية للقراءة عبر Junction، دون `composer install/update/dump-autoload` على هذا المسار. جميع caches وجداول الاختبار وقوالب Blade المجمعة داخل sandbox.
- قاعدة الاختبار SQLite؛ نزيلان وغرفتان وحجوزات اصطناعية وبريد `example.invalid`. تم تفعيل الإضافات المطلوبة في **إعدادات قاعدة الاختبار فقط**.
- نجح `artisan about` و`route:list` وmigrations الأساسية ومهاجرات الإضافات و`view:cache`، ثم شُغل خادم localhost من مجلد `public`.
- فحص HTTP تم في وضع `local` مع جلسات محلية. المقارنة الوحيدة بوضع `production` كانت داخل sandbox لإثبات سلوك CSRF، ثم أُعيد الوضع المحلي.
- مسار الدفع المختبر تحويل بنكي يسجل دفعة محلية معلقة؛ لم يحدث اتصال ببنك أو بوابة دفع. محاولة تشغيل `/usr/sbin/sendmail` في بيئة Windows فشلت؛ هذا ليس اختبار تسليم بريد خارجي ناجحًا.
- بعض اختبارات الدوال استخدمت stubs لإعدادات الفندق، hooks وواجهات مساعدة فقط؛ لم تغير الخوارزمية المختبرة. تم تأكيد النتائج الأهم أيضًا عبر HTTP وقاعدة الاختبار.
- قياسات الزمن المحلية تشمل تشغيل PHP على Windows وقراءة الملفات؛ ليست قياسات أداء الإنتاج أو Core Web Vitals.
- أُوقف خادم الاختبار بعد انتهاء المراجعة.

## 5. نتائج الأمان

### S01 — تعطيل حماية CSRF للإدارة في الإنتاج

**الأولوية: عاجلة. الحالة: مثبت بالكود، وباختبار الدالة، وبمقارنة HTTP محلية.**

[platform/core/base/src/Providers/EventServiceProvider.php:187](D:/الفندق/hotel-source-github/public_html/platform/core/base/src/Providers/EventServiceProvider.php:187) يستبدل `ValidateCsrfToken` بـ`BaseMiddleware` عندما تكون البيئة `production` والطلب داخل الإدارة. يحدث ذلك في حدث `RouteMatched`، وليس مجرد إعداد معطل غير مستخدم.

في sandbox، POST لنموذج الإدارة بدون CSRF رفضه الوضع المحلي برسالة `CSRF token mismatch` داخل JSON بحالة HTTP 200. نفس الطلب في وضع الإنتاج وصل إلى التحقق من كلمة المرور وأعاد HTTP 422. اختبار الدالة أعاد اسم middleware الذي يتجاوز الفحص.

**الأثر:** إزالة حاجز أمني مهم من طلبات الإدارة. لم أجرب تغيير بيانات كمسؤول ولم أثبت سرقة جلسة أو استغلالًا على الإنتاج. شروط الاستغلال تتأثر بالمتصفح والكوكيز والطلبات والإعدادات الأخرى؛ SameSite ليس بديلًا تلقائيًا عن هذا الفحص.

**المطلوب لاحقًا:** حماية CSRF لكل عمليات الإدارة، وحصر استثناءات webhooks المحددة عند الحاجة. **معيار القبول:** رفض أي طلب إدارة مؤثر بدون token صالح في وضع الإنتاج، مع نجاح الطلب المشروع وعدم كسر webhook الموقّع.

مرجع: [OWASP CSRF](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html).

### S02 — التقويم العام يكشف بيانات شخصية للنزيل

**الأولوية: عاجلة. الحالة: مثبت عبر HTTP ببيانات اصطناعية.**

المسار العام `ical/{slug}` موجود في [platform/plugins/hotel/routes/web.php:310](D:/الفندق/hotel-source-github/public_html/platform/plugins/hotel/routes/web.php:310). التصدير يستخدم [platform/plugins/hotel/src/Services/ICalService.php:25](D:/الفندق/hotel-source-github/public_html/platform/plugins/hotel/src/Services/ICalService.php:25) و[platform/plugins/hotel/src/Services/ICalService.php:65](D:/الفندق/hotel-source-github/public_html/platform/plugins/hotel/src/Services/ICalService.php:65)، ويضم الاسم والبريد والهاتف وتواريخ الإقامة ورقم الحجز للنزيل المرتبط بالحجز.

**المطلوب لاحقًا:** بيانات توافر غير شخصية، مع token مستقل قابل للإلغاء أو تحكم وصول مناسب لوظيفة التكامل. **معيار القبول:** الزائر غير المصرح له لا يستطيع استخراج هوية أي نزيل؛ feed المصرح به لا يحتوي بيانات شخصية غير لازمة.

### S03 — تحكم الزائر في حقول حجز داخلية عبر Mass Assignment

**الأولوية: عاجلة. الحالة: مثبت بالدالة ثم بحفظ سجل عبر HTTP.**

[platform/plugins/hotel/src/Http/Controllers/PublicController.php:464](D:/الفندق/hotel-source-github/public_html/platform/plugins/hotel/src/Http/Controllers/PublicController.php:464) يمرر الطلب كله إلى Booking. النموذج [platform/plugins/hotel/src/Models/Booking.php:21](D:/الفندق/hotel-source-github/public_html/platform/plugins/hotel/src/Models/Booking.php:21) يقبل `status/customer_id/payment_id/currency_id`. إعادة حساب المبلغ لا تحمي هذه الحقول. `customer_id` يُستبدل فقط عند وجود عميل مسجل الدخول؛ الحجز كزائر بقي قابلًا للتأثير.

اختبار زائر أرسل `status=completed` و`customer_id=2` إلى checkout. السجل الاصطناعي حُفظ بهاتين القيمتين، رغم أن مسار التحويل البنكي سجل دفعة معلقة. اختبار تعبئة النموذج قبل الحفظ أظهر أيضًا قبول `payment_id` و`currency_id`؛ لم أثبت استغلال كل حقل منها في دفع حي.

**الأثر:** تزوير حالة الحجز وإسناده إلى نزيل آخر، واختلال الفصل بين حالة الحجز وحالة الدفع.

**المطلوب لاحقًا:** قائمة حقول مسموح بها للطلب العام؛ مصدر الحالة والعميل والدفع من الخادم والجلسة. **معيار القبول:** إرسال هذه الحقول الإضافية لا يغير القيم المحكومة من الخادم، والدفعة المعلقة لا تحول الحجز إلى مدفوع/مكتمل.

### S04 — استيراد تقويم يقبل قراءة ملف محلي وخطر SSRF

**الأولوية: مرتفعة. الحالة: قبول `file://` مثبت في الدالة؛ استغلال كامل عبر حساب إدارة لم يُختبر.**

[platform/plugins/hotel/src/Services/ICalService.php:218](D:/الفندق/hotel-source-github/public_html/platform/plugins/hotel/src/Services/ICalService.php:218) يمرر URL إلى cURL، مع تتبع التحويلات، دون allowlist للبروتوكول أو المضيف أو منع العناوين الداخلية في الدالة. [platform/plugins/hotel/src/Http/Controllers/ICalController.php:53](D:/الفندق/hotel-source-github/public_html/platform/plugins/hotel/src/Http/Controllers/ICalController.php:53) و`update` يستقبلان URL من `Request` عام ويخزنانه؛ الوصول لهذه العمليات داخل مسارات الإدارة.

في الاختبار قرأت الدالة ملف marker اصطناعيًا من `file://` وأعادت محتواه. لم أقرأ `.env` أو ملفًا حقيقيًا حساسًا، ولم أرسل طلبًا لشبكة داخلية أو metadata خدمة سحابية. قبول الملف لا يثبت وحده طريقة تسريب محتواه للمتصفح؛ يثبت وصول دالة الجلب إليه، مع غياب الضوابط المذكورة.

**المطلوب لاحقًا:** السماح بـHTTPS ومصادر تقويم معتمدة، وفحص الوجهة الفعلية بعد DNS والتحويلات، ومنع localhost/private/link-local، وحدود حجم/زمن. **معيار القبول:** رفض `file://` والوجهات الداخلية والتحويل إليها، مع نجاح تقويم خارجي معتمد. راجع [OWASP SSRF](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html).

### S05 — تنبيهات أمان في الإصدارات المقفلة

**الأولوية: مرتفعة، وتتحدد شدة كل بند حسب إمكانية الوصول إليه. الحالة: فحص Composer رسمي بتاريخ التقرير.**

أمثلة مهمة: Laravel 12.43.1، Dompdf 3.1.4، Guzzle 7.10.0، PhpSpreadsheet 1.30.1، Twig 3.22.2، Jmespath 2.8.0. جدول الحزم والتنبيهات وروابط النشرات في الملحق الآلي أدناه وملفات JSON.

وجود المكتبة لا يثبت استغلال كل advisory في الفندق. مثال AWS يتعلق بوظيفة CloudFront التي لم أثبت استخدامها، وبيئة الإنتاج الحالية الرئيسية لديها `APP_DEBUG=false`، وهذا يقلل نطاق بعض تنبيهات debug ولا يعالج البقية. PHPUnit وSymfony YAML المذكوران في فحص الكل من تبعيات التطوير، وليس دليل نشرهما على الخادم.

**المطلوب لاحقًا:** حصر المسارات المستخدمة مثل الفواتير/import/templates، وتحديث متوافق مع المنصة والـlockfile، واختبارات ارتداد. لا تنفذ `composer update` شاملًا دون خطة توافق. [شرح Composer audit](https://getcomposer.org/doc/03-cli.md#audit).

### S06 — كوكيز الجلسة مضبوطة بدون Secure في النسخ الأصلية

## 6. مشاكل الوظائف والحجز

### F01 — بحث الحجز الخارجي لا ينقل اختيارات النزيل

**الأولوية: P0 لتجربة الحجز المباشر. الحالة: سبب مؤكد بالكود، ومطابق للفحص الحي السابق.**

[platform/themes/riorelax/partials/hotel/forms/form.blade.php:132](D:/الفندق/hotel-source-github/public_html/platform/themes/riorelax/partials/hotel/forms/form.blade.php:132) يعرض في style 2 رابطًا إلى `external_booking_url` بدل زر إرسال للنموذج. لا يبني URL من الوصول والمغادرة والبالغين والأطفال والغرف. روابط الكارت وSidebar وقسم booking-form تفتح الوجهة نفسها أيضًا.

### F02 — checkout لا يعيد فحص المخزون ولا يلتزم بجلسة الحجز

**الأولوية: P0 للحجز الداخلي. الحالة: مثبت عبر HTTP والحفظ في SQLite.**

[platform/plugins/hotel/src/Http/Controllers/PublicController.php:424](D:/الفندق/hotel-source-github/public_html/platform/plugins/hotel/src/Http/Controllers/PublicController.php:424) يفحص وجود token فقط، ثم يقرأ الغرفة والتواريخ وعدد الغرف من الطلب النهائي. لا يقارنها بقيم جلسة البداية، ولا يفحص `isAvailableAt` مرة أخرى قبل الحفظ. `CheckoutRequest` يضع حدًا أدنى للغرف دون حد مرتبط بالمخزون.

بدأ الاختبار بغرفة 1، 20–22 أكتوبر، غرفة واحدة. checkout أرسل غرفة 2 **غير منشورة** بمخزون غرفة واحدة، 23–25 أكتوبر، وعدد 9999. السجل حُفظ بالغرفة والتواريخ والعدد المعدل، وأعاد الطلب النهائي صفحة نجاح HTTP 200 مع تشغيل إضافة الدفع ومسار التحويل البنكي المحلي.

لم أنفذ اختبار ضغط أو سباق طلبين. غياب transaction/lock في مسار checkout يضيف احتمال حجز متزامن زائد، لكنه يحتاج اختبارًا مستقلًا على MySQL قبل تقدير حجمه.

**المطلوب لاحقًا:** التحقق من نشر الغرفة والتواريخ والإشغال والتوافر عند الحفظ، وتحديد مصدر معايير الحجز، وربط التحديثات بعملية ذرية. معيار القبول: طلب معدل لا يحجز غرفة مختلفة أو كمية أعلى من المخزون؛ آخر غرفة لا تُباع مرتين بالتزامن.

### F03 — السعر الخاص لا يُضرب في عدد الغرف

**الأولوية: مرتفعة. الحالة: مثبت بالدالة على بيانات اصطناعية.**

### F04 — مدخلات حساب التكلفة تقبل أعدادًا سالبة وتحقق تاريخ غير صحيح

**الأولوية: مرتفعة. الحالة: مثبت بالدالة وبـHTTP.**

**معيار القبول:** رفض الإشغال والكميات غير الصالحة والتواريخ المعكوسة، وعدم عرض قيمة تختلف إشارتها عن المبلغ الخام؛ قواعد موحدة بين البحث والعرض والتأكيد.

### F06 — البحث يسكت عن التواريخ الخاطئة ويقبل حدودًا غير منضبطة

**معيار القبول:** أخطاء مفهومة للمدخلات غير الصحيحة، وحد أعلى للنتائج ومدى التاريخ، وإجمالي وصفحات يطابقان النتائج المتاحة فعليًا.

### F07 — بحث AJAX للغرف ينهار

### F09 — نقص ترجمة الثيم مؤكد

**معيار القبول:** قاموس معتمد لكل لغة، ومقارنة نفس الصفحة/القوائم/الغرف/النشرة على EN/AR/ZH، مع مراجعة لغوية بشرية للعربي والصيني.

### F10 — فشل بريد موثق في سجلات الأصل

**الأولوية: مرتفعة للتشغيل والثقة. الحالة: دليل تاريخي من الملفات المرفقة، لا اختبار SMTP حي.**

أثر محتمل على الاستفسارات وتأكيد الحساب/الحجز وإعادة كلمة المرور؛ يلزم ربط كل حدث برسالته. `QUEUE_CONNECTION=sync` في الأصل يجعل بعض المهام تعمل مع الطلب مباشرة، لكنه لا يثبت وحده بطء الإنتاج.

**معيار القبول:** مسار إرسال معتمد واختبار تسليم فعلي لحساب اختبار يملكه الفندق، وتسجيل/تنبيه للفشل، دون اعتبار HTTP 200 دليل وصول الرسالة.

### F12 — تفاصيل تحتاج معالجة قبل التوسع في المكونات

**الأولوية: تحسين/تحقق إضافي، وليست كلها أعطال مثبتة.**

- حقول نموذج البحث تستخدم IDs ثابتة مثل `adults` و`toggle-guests-and-rooms`؛ وJS يحدث العدادات باستعلام عالمي. عند عرض نموذجين في الصفحة قد يتداخل التحكم. المصدر: `partials/hotel/forms/form.blade.php` و`assets/js/main.js`. لم أعد إنتاج صفحتين متداخلتين ببيانات الإنتاج.
- بيانات إضافات الخدمة/الطعام في CheckoutRequest تتحقق كمصفوفة فقط، دون قواعد لكل ID أو published status؛ بعض الحفظ يستخدم IDs الأصلية. تحتاج اختبارات سعر الخدمات والفهرسة والـFK وتطابق البيانات المعروضة والمحفوظة.
- تسجيل العميل وتغيير كلمة المرور يكتفيان بحد أدنى ستة أحرف. تحسين مقترح لسياسة العملاء، وليس دليل تجاوز تسجيل الدخول. تغيير كلمة المرور يتحقق من القديمة، وهذه نقطة جيدة.
- إعادة إرسال تأكيد التسجيل تستخدم GET مع email ورسائل تكشف وجود العميل؛ يلزم اختبار حماية الإساءة والحدود. لم أرسل رسائل أو أجرب قائمة حسابات.
- تقويم iCal يزيد DTEND يومًا ويسترجع يومًا في الاستيراد. بما أن باقي الحجز يستخدم end_date حدًا حصريًا لليالي، يوجد احتمال انزياح يوم مع منصات تقويم أخرى. يحتاج اختبار round-trip وعقد تاريخ مع المزود؛ لم أنسبه كعطل OTA مثبت.
- حين عُطلت إضافة الدفع في fixture، checkout حفظ جزءًا من الحجز ثم انتهى 500 لغياب `Botble\Payment\Models\Payment`؛ مع تفعيلها نجح مسار الاختبار. هذا يبين اقترانًا فعليًا بالإضافة، ولا يثبت أن الدفع معطل على الموقع الحي.

## 9. حدود التغطية وما لم يُحسم

هذه مراجعة واسعة موجهة للمخاطر، وليست ادعاء فحص كل سطر في 54 ألف ملف أو شهادة خلو من الثغرات.

- لم أستخدم قاعدة إنتاج أو بيانات نزلاء حقيقية، أو اعتماد مسؤول، أو كلمات مرور الاستضافة.
- لم أتحقق من المستخدم الإداري القديم أو إنشاء/صلاحيات هانيا، MFA أو إلغاء الجلسات، ومن ملكية الحسابات الخارجية.
- SQLite لا تثبت سلوك MySQL في locks وcollation والـFK والتزامن. نجاح migrations المحلية ليس تأكيدًا لترقية إنتاج آمنة.
- لم أختبر بوابات الدفع الخارجية أو استرداد الأموال أو webhooks/replay والمصالحة، ولا تكامل مخزون/أسعار Aiosell.
- لا توجد بيانات محتوى الإنتاج أو صورها في fixture؛ لم أجر مقارنة بصرية أو اختبار استخدام كامل لكل صفحة/لغة/جهاز، ولا Accessibility شامل أو قياس Web Vitals.
- لم أنفذ تحميلًا هجوميًا أو SQL injection/XSS على الموقع الحي. استعمال Query Builder وclean في مواضع مفحوصة لا يثبت خلو المشروع كله من SQLi/XSS.
- الاختبارات الموجودة في `tests/` أمثلة عامة فقط. تبعيات الأصل production-only ولا تحتوي PHPUnit التنفيذي؛ لذلك لم أسجل نجاح PHPUnit. الاختبارات التي نفذتها مرفقة مستقلة خارج الكود.
- أسرار `.env` مستبعدة من Git وفق استيراد السورس وفحصه السابق؛ لم أنسخ قيمها إلى التقرير. لم أنفذ الآن تاريخًا كاملًا لكل commit خارج الـinitial import أو فحص أسرار الاستضافة.
