## حماية إضافية ضمن نفس المسار

- جلب الشبكة خارج قفل المخزون، مع sync_version دائم يرفض نتيجة تنزيل قديمة إذا تغير/تزامن المصدر أثناء التنزيل.
- التحقق من كل أحداث snapshot قبل تطبيقها، بما فيه الأحداث المفقودة والملغاة؛ تبديل تواريخ حدثين يتم تقييمه بحسب الحالة النهائية، وليس خطوة بخطوة على مخزون قديم.
- نقص UID، تكرار UID أو خصائص أساسية، مصدر HTML أو ناقص، وحدث غير صالح يرفض المصدر بدل تحرير حجوزاته بالخطأ.
- تقويم متكرر أو معتمد على DURATION دون نطاق مباشر يُرفض صراحة ويحافظ على المخزون السابق. لا توجد معالجة كاملة لتكرار RFC 5545 في هذا التطبيق.
- تواريخ all-day تبقى تواريخ تقويمية؛ التوقيت الصريح UTC أو TZID يتحول إلى app.timezone قبل استنتاج ليالي الفندق.
- فشل كتابة صف الحجب يُرجع معاملة إنشاء الحجز، ولا يترك كتابة جزئية.
- حذف مصدر من الإدارة يحرر حجبه المعرّف فقط تحت قفل الغرفة. تغيير إعداد المصدر يرفع revision لمنع اعتماد تنزيل سابق.
- واجهة API للمزامنة ترجع error=true عند وجود مصدر فاشل، حتى لا تعرض الإدارة نجاحًا كاملًا لحالة فشل.
- تعارض السعة يرفض snapshot كله، ويحافظ على الحالة السابقة ويسجل warning/conflict. الحجز الخارجي الذي لا يمكن استيعابه يحتاج تدخل تشغيل لحل التعارض؛ لا يتم تجاهل السعة أو ادعاء نجاح الاستيراد.

## التحقق

- نفس PHP 8.3.35 والاعتماديات المحلية المنفصلة؛ MariaDB 11.8.9 / InnoDB، قاعدة صناعية فارغة على loopback فقط. لا استعادة لبيانات الفندق أو تغيير لها.
- اختبارات الحجز المتزامن الأربع السابقة بقيت ناجحة: عملية واحدة تحجز وثلاث تُرفض.
- السباق بين الحجز والتقويم أُعيد بحاجز بين عمليتين PHP مستقلتين، ثم أضيف الاتجاه المعاكس بقفل الاستيراد أولًا. هذه اختبارات محددة، وليست إثباتًا لكل حالات الضغط أو كل كاتب مخزون بالإدارة.
- migration الحقيقي نُفذ في قاعدة الاختبار؛ rollback وإعادة التطبيق نجحا.
- اختبارات الأمان والباك إند الأساسية السابقة نجحت 49/49 على SQLite، ثم نجحت ضمن مجموعة MariaDB الموسعة.
- PHP lint للملفات العشرة المعدلة/الجديدة في هذه الجولة نجح، وgit diff --check لم يعرض أخطاء whitespace.
- مقارنة SHA256 لـ249 ملفًا في plugins/stripe وplugins/paypal وplugins/payment: **صفر ملفات متغيرة**.
- قاعدة الاختبار أُزيلت والخادم المؤقت أُوقف بعد حفظ الأدلة. لا خدمة تطوير تعمل بسبب هذه الجولة.

## قبل النشر — لم يُنفذ على الإنتاج

**متابعة:** تمت استعادة قاعدة SQL المقدمة كاملة وتطبيق الترقية على نسخة staging محلية. لا مصادر تقويم أو سجلات مزامنة أو حجب ICAL في الملف المتاح. النسخة المحدثة صُدرت واختُبرت استعادتها. التفاصيل في [DATABASE_UPGRADE_REPORT_2026-10-05.md](DATABASE_UPGRADE_REPORT_2026-10-05.md). الإنتاج لم يُعدل.

هذه النسخة تحتاج migration الهوية قبل تشغيل مسار المزامنة الجديد. يضيف حقلي `ical_calendar_id` و`ical_uid_hash` وفهرسًا فريدًا إلى ht_booking_rooms، وحقل `sync_version` إلى ht_room_calendars. حقول الهوية nullable للحجوزات المحلية والصفوف القديمة.

**الحجب المستورد قديمًا لا يحمل مصدرًا أو UID محفوظًا.** لا يمكن استنتاجهما بأمان من التواريخ أو بادئة ICAL وحدها، لذلك لم تُنسب الصفوف القديمة تلقائيًا إلى مصدر ولم تُحذف. هذه الصفوف تبقى حجبًا محافظًا وقد تتداخل مع استيراد جديد أو تمنعه؛ تحتاج مطابقة مدروسة مع مصادر الفندق قبل تفعيل المزامنة على الإنتاج.

استعلام قراءة لتحديد حجم هذه الحالات، بعد تنفيذ migration على بيئة تجريبية مستعادة من نسخة قاعدة الفندق:

```sql
SELECT br.id, br.room_id, br.booking_id, br.start_date, br.end_date
FROM ht_booking_rooms br
JOIN ht_bookings b ON b.id = br.booking_id
WHERE b.booking_number LIKE 'ICAL-%'
  AND br.ical_calendar_id IS NULL
  AND b.status <> 'cancelled';
```

مسار الترقية المقترح: نسخة قاعدة احتياطية، تجربة migration على staging، مطابقة الحجب القديم مع مصدره بدل الحذف أو الدمج بالتواريخ، مزامنة مصادر حقيقية والتحقق من السعة والتعارضات، ثم نشر مضبوط. لم يُشغل الاستعلام على بيانات المستخدم هنا، ولم يُنفذ نشر.

rollback مخطط الهوية بعد استخدامه يزيل معلومات الربط؛ لا يُستخدم كبديل عن استعادة نسخة متوافقة من الكود والقاعدة عند الرجوع من نشر فعلي.
